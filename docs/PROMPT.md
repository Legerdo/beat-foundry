# Rhythm Incremental Game — Autonomous One-Shot Development Prompt

현재 작업공간에서 **리듬과 음악 자체가 성장 시스템이 되는 고품질 인크리멘탈 게임**을 실제로 완성하라.

아이디어 제안, 디자인 문서, 기술 데모 또는 프로토타입을 만드는 것이 목적이 아니다.

직접 설계하고 구현하고 실행하고 플레이해 보면서 문제를 수정하여, 짧더라도 하나의 완성된 게임 경험으로 마무리하라.

## 기본 전제

Claude Opus 5.5 High 이상 환경을 대상으로 한다.

단, reasoning / thinking / effort는 현재 환경에서 이미 설정된 값을 우선하며 이 프롬프트에서 별도로 강제하거나 변경하지 않는다.

모델의 판단력을 적극적으로 사용하라.

세부적인 설계와 구현 방법을 지시받으려고 멈추지 말고, 목표와 품질 기준을 만족시키는 방법을 스스로 선택한다.

핵심적인 모호함 때문에 서로 완전히 다른 게임이 만들어질 정도가 아니라면 질문하지 말고 진행한다.

---

# 게임의 핵심

게임은 아주 단순한 비트 또는 음악적 pulse에서 시작한다.

플레이가 진행되면서 새로운 리듬, 악기, 음색, 자동화, 상호작용과 시각적 시스템이 추가되고, 처음의 작은 비트가 점점 거대한 음악 시스템으로 성장해야 한다.

가장 중요한 원칙은:

**음악의 성장과 인크리멘탈 성장 자체를 같은 시스템으로 만든다.**

새로운 음악 요소가 추가되는 것은 단순히 BGM이 풍부해지는 것이 아니라 새로운 생산 방식, 시너지 또는 전략을 의미해야 한다.

반대로 경제적 성장은 숫자만 증가시키는 것이 아니라 실제 음악과 화면에도 느껴지는 변화를 만들어야 한다.

플레이어는 게임 후반에 자신의 성장 상태를 숫자뿐 아니라 **듣고 보는 것만으로도 느낄 수 있어야 한다.**

---

# 핵심 경험

플레이어가 느껴야 하는 흐름은 대략 다음과 같다.

**작은 비트  
→ 직접 리듬에 개입  
→ 새로운 음악 요소 발견  
→ 생산과 음악이 서로 연결됨  
→ 자동화와 시너지 형성  
→ 음악과 화면이 점점 풍부해짐  
→ 긴장감이 축적됨  
→ 강력한 DROP 또는 이에 준하는 음악적 climax  
→ 더 큰 성장  
→ 하나의 곡이나 공연을 완성  
→ 새로운 run으로 이어지는 장기 성장**

구체적인 시스템, 자원, 악기 구성, progression 구조는 이 경험을 가장 잘 살릴 수 있도록 직접 설계하라.

---

# 리듬과 인크리멘탈의 관계

일반적인 리듬게임에 숫자 성장 시스템을 붙이지 마라.

반대로 일반적인 idle/clicker에 박자 맞추기 미니게임만 붙이지도 마라.

둘이 서로 떼어낼 수 없을 정도로 통합되어야 한다.

플레이어의 리듬 입력은 의미 있는 보상을 주되, 계속 클릭하거나 키를 두드리는 노동이 게임의 중심이 되어서는 안 된다.

성장할수록 플레이어가 구축한 음악 시스템이 스스로 연주하고 생산하기 시작해야 한다.

숙련된 수동 플레이는 자동화를 대체하기보다는 강화하거나 변주하는 방향이 좋다.

---

# 음악

초기에는 의도적으로 단순해야 한다.

성장하면서 실제로 듣기 좋은 음악으로 발전해야 한다.

리듬 레이어, 저역, 퍼커션, 화성, 멜로디, 전환 효과, variation 등 무엇을 사용할지는 직접 판단한다.

단순한 메트로놈에 효과음만 추가한 수준으로 끝내지 마라.

반복 루프라도 progression, variation, build-up, breakdown, climax 등을 통해 음악적으로 변화해야 한다.

가능하다면 외부 저작권 음원에 의존하지 않고 자체 생성 또는 프로젝트에 적합한 방식으로 구성한다.

리듬 정확도는 렌더링 프레임레이트에 종속되지 않는 안정적인 시간 기준을 사용한다.

---

# DROP과 Climax

이 게임에서 가장 강한 순간 중 하나는 음악적 climax다.

반드시 EDM의 전형적인 DROP을 그대로 복제할 필요는 없다.

게임의 음악적 정체성에 더 적합한 형태가 있다면 자유롭게 설계한다.

중요한 것은:

- 이전 상태와 분명한 대비가 있고
- anticipation이 있으며
- 음악과 화면과 생산 시스템이 동시에 반응하고
- 플레이어가 자신의 성장이 폭발했다는 느낌을 받고
- 게임이 진행될수록 그 순간도 함께 성장하는 것

이다.

평범한 행동과 최고조의 연출이 같은 체급으로 보여서는 안 된다.

---

# Game Feel / Juice

게임 필은 마지막에 파티클을 뿌리는 작업이 아니다.

입력, 구매, unlock, rhythm success, synergy, climax 같은 중요한 행동은 즉각적이고 읽기 쉬운 피드백을 가져야 한다.

필요에 따라 다음을 조합하라.

- animation
- easing
- squash / stretch
- scale response
- particles
- trails
- waveform 또는 audio-reactive motion
- anticipation
- impact
- follow-through
- sound accents
- camera response
- brief visual holds
- floating feedback
- UI motion

하지만 **효과의 양이 아니라 대비와 타이밍**을 우선한다.

항상 흔들리고 항상 번쩍이고 항상 파티클이 터지면 아무것도 특별하지 않다.

작은 성공, 큰 성공, unlock, climax가 서로 다른 체급을 가져야 한다.

특히 rhythm timing이나 오디오 재생 자체를 시각적 hit-stop 때문에 망가뜨리지 마라.

---

# 시각적 방향

게임처럼 보여야 한다.

일반적인 웹 대시보드에 네온 카드와 숫자를 붙인 UI로 만들지 마라.

음악과 성장 시스템 자체가 화면의 주인공이어야 한다.

현재 음악의 구조와 활동 상태를 화면에서 직관적으로 느낄 수 있는 시각 언어를 직접 설계한다.

아트 스타일, 색상, 레이아웃, 모션 디자인, 세계관은 자유롭게 선택하되 하나의 명확한 visual identity를 유지한다.

외부 에셋이 반드시 필요하지 않다면 procedural graphics, geometry, shaders, particles, typography, audio-reactive visuals 등을 적극 활용할 수 있다.

---

# 성장 구조

진행하면서 숫자뿐 아니라 **게임의 표현력과 상호작용 자체가 성장**해야 한다.

좋은 progression은 새로운 선택, 음악적 변화, 자동화, 시너지 또는 spectacle을 제공한다.

단순히 동일한 효과에 수치만 계속 곱하는 업그레이드 목록으로 채우지 마라.

필요하다면 prestige 또는 run reset 구조를 사용하되 세계관과 음악 경험 안에서 자연스럽게 표현한다.

새 run은 이전 run을 그대로 처음부터 반복하는 것이 아니라 영구적인 변화나 가속을 느끼게 해야 한다.

게임에는 명확한 장기 목표와 하나의 finale가 있어야 한다.

완료 이후 계속 플레이할 수 있는 구조를 선택하는 것은 자유다.

---

# 접근성 및 UX

첫 실행 후 플레이어가 긴 설명서를 읽지 않아도 기본 행동을 빠르게 이해할 수 있게 한다.

튜토리얼 팝업을 연속해서 띄우기보다 인터랙션과 피드백으로 가르치는 것을 우선한다.

음량 조절, 과도한 화면 흔들림이나 flash를 완화할 방법 등 실제 플레이에 필요한 설정을 제공한다.

UI는 현재 행동과 다음 목표를 쉽게 읽을 수 있어야 한다.

정보를 많이 보여주는 것보다 필요한 정보를 적절한 순간에 보여주는 쪽을 택한다.

---

# 기술적 자율성

현재 프로젝트가 있다면 먼저 구조와 코드를 실제로 확인하고 기존 기술 스택을 존중한다.

비어 있는 작업공간이라면 이 게임을 가장 잘 구현할 수 있는 적절한 웹 기술을 직접 선택한다.

TypeScript, Canvas, WebGL, Phaser, PixiJS, Three.js, Web Audio API 또는 다른 적절한 기술을 사용할 수 있다.

특정 라이브러리를 사용하는 것이 목적은 아니다.

**실제 게임 품질과 유지 가능한 구현을 만드는 것이 목적이다.**

불필요한 프레임워크, 추상화, 미래 확장용 구조를 만들지 않는다.

오디오 timing, rendering, gameplay state, persistence처럼 실제로 책임이 다른 부분만 합리적으로 분리한다.

외부 에셋과 라이브러리는 실제 품질 향상에 도움이 될 때만 사용한다.

# 개발 방식

먼저 프로젝트와 사용 가능한 도구를 파악한 뒤 필요한 설계를 세우고 바로 구현한다.

계획서만 작성하고 멈추지 않는다.

구현 중에는 실제 게임을 반복해서 실행해 플레이 경험을 확인한다.

특히 다음을 직접 판단한다.

- 처음 봐도 플레이 방법이 이해되는가
- 리듬 입력이 만족스러운가
- 음악이 성장하고 있다는 느낌이 실제로 드는가
- 자동화 이후에도 플레이어가 개입할 이유가 있는가
- progression에 지루한 구간이 없는가
- 새로운 시스템이 실제 변화를 만드는가
- climax가 충분히 강한가
- 효과의 계층이 읽히는가
- UI가 게임보다 앞에 나오지 않는가
- 후반이 초반보다 확실히 장관인가

문제가 보이면 원인을 찾아 수정한다.

테스트만 통과하도록 하드코딩하거나 실제 문제를 숨기지 않는다.

필요한 자동 테스트와 실제 실행 검증을 적절히 사용하되, 검증 자체가 목적이 되어 끝없이 반복하지 않는다.

# 마지막 원칙

이 문서는 세부 설계서가 아니다.

**무엇을 만들어야 하고 어떤 경험이어야 하는지에 대한 방향과 품질 기준이다.**

나머지는 Claude Opus 5.5의 설계·구현·미적 판단을 적극적으로 사용하라.

요구사항을 체크리스트처럼 기계적으로 소화하지 말고 서로 연결된 하나의 게임으로 설계한다.

더 좋은 아이디어를 발견했다면 핵심 정체성을 지키는 범위에서 과감하게 적용한다.

최종 목표는 기능 목록을 채우는 것이 아니라:
